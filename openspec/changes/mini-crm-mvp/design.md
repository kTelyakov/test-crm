# Design

## Context

Проект новый (greenfield). Мотивация и состав изменений — в `proposal.md`, требования — в `specs/`. Ограничения: срок 2–3 часа, обязательный Supabase (Auth, миграции), фронтенд по FSD, бэкенд по DDD, читаемый код, открытая регистрация отключена, серверные ключи не попадают во фронтенд и в репозиторий.

## Goals / Non-Goals

**Goals:**
- Доменные правила (переходы, роли, комментарии) живут в одном месте — в доменном слое бэкенда — и покрыты юнит-тестами без БД.
- Статус задачи и история не могут быть подделаны ни через бэкенд, ни напрямую через Supabase API.
- Интерфейс и сервер используют одну и ту же таблицу переходов (без рассинхронизации правил).

**Non-Goals:**
- Уведомления, вложения, комментарии вне истории статусов, отчёты, мультитенантность.
- Управление пользователями из интерфейса (пользователей создаёт администратор вручную или сидом).
- Полноценный CI/CD.

## Decisions

### 0. Технологический стек

| Область | Выбор | Почему |
|---|---|---|
| Монорепозиторий | pnpm workspaces (`frontend`, `backend`, `e2e`) | Один `install`, общие скрипты |
| Фронтенд: сборка | Vite + React 18 + TypeScript (strict) | Стандарт, быстрый старт |
| Роутинг | React Router | Простые маршруты и guards по роли |
| Серверное состояние | TanStack Query (хуки генерирует Orval) | Кэш, инвалидация после смены статуса |
| Клиентское состояние | Zustand, только сессия (пользователь, роль) в `entities/user` | Минимум кода; остальные данные серверные |
| Формы и валидация | React Hook Form + Zod | Типобезопасные формы |
| UI и стили | Tailwind CSS + shadcn/ui | Аккуратный интерфейс без ручной вёрстки |
| Контроль FSD | Steiger | Проверка границ слоёв |
| Качество кода | ESLint + Prettier | Читаемость |
| Бэкенд | Node.js, TypeScript, Fastify, Zod | См. решения 1–2 и 9 |
| Тесты | Vitest (домен), Playwright (UI и API) | См. решение 8 |

**Правило состояния:** серверные данные (объекты, задачи, история) живут только в TanStack Query и не дублируются в сторе; Zustand хранит только сессию; остальное — локальный `useState`. Идентификаторы берутся из URL (`useParams`), а не пробрасываются пропсами.

*Отвергнуто:* Recoil — разработка остановлена, репозиторий заархивирован; Redux Toolkit — избыточен, клиентского состояния почти нет; Jotai — равноценная альтернатива Zustand, выбран более распространённый; Ant Design/MUI — тяжелее и менее гибкие для минимального интерфейса.

### 1. Архитектура: Supabase + отдельный DDD-бэкенд (вариант A)
Браузер → бэкенд (Node.js, TypeScript, Fastify) → Supabase (Postgres + Auth). Фронтенд ходит в Supabase только за входом (`anon`-ключ), все данные получает через API бэкенда.
*Альтернатива:* только Supabase (RLS + RPC) — быстрее, но доменная логика уходит в PL/pgSQL, DDD становится номинальным, а ошибка в политике RLS сразу превращается в уязвимость без страховки.

### 2. Бэкенд: DDD-модули
```
backend/src/
  modules/
    identity/   domain: User, Role | application: AuthenticateUser | infrastructure: проверка JWT, ProfileRepository | presentation: auth-middleware
    sites/      domain: Site | application: Create/Update/Delete/List/GetSite | infrastructure: SupabaseSiteRepository | presentation: routes + Zod DTO
    tasks/      domain: Task (агрегат), TaskStatus, TaskAction, StatusTransition, HistoryEntry, ошибки
                application: CreateTask, UpdateTask, DeleteTask, AssignTask, ChangeTaskStatus, GetTask, ListTasks, ListMyTasks
                infrastructure: SupabaseTaskRepository | presentation: routes + Zod DTO
  shared/       DomainError, Clock, конфиг, обработчик ошибок
```
Правила зависимостей: `domain` ничего не импортирует из других слоёв; `application` зависит от `domain` и интерфейсов репозиториев (порты); `infrastructure` реализует порты; `presentation` вызывает use cases. Домен не знает про Supabase и HTTP.

### 3. Агрегат Task и таблица переходов
`Task.changeStatus(action, actor, comment?)` проверяет: переход есть в таблице, роль и (для исполнителя) назначение, обязательность комментария. Возвращает новое состояние и `HistoryEntry`. Таблица переходов — единственный источник правды; для фронтенда бэкенд отдаёт в ответе задачи список `availableActions`, посчитанный тем же доменным кодом, поэтому правила не дублируются на клиенте.
*Альтернатива:* считать доступные действия на клиенте (`getAvailableActions` в FSD-сущности) — проще, но дублирует правила. Отвергнуто в пользу одного источника правды.

### 4. Атомарность статуса и истории
Репозиторий сохраняет изменение через SQL-функцию `apply_task_transition(task_id, expected_from_status, to_status, actor_id, comment)`, выполняющую `UPDATE` и `INSERT` истории в одной транзакции; в `UPDATE` проверяется `expected_from_status` (оптимистичная блокировка от гонок: два одновременных перехода не пройдут оба). Функция доступна только роли `service_role`.

### 5. Безопасность БД
- RLS включён на всех таблицах; политик для `anon` и `authenticated` на запись нет, прямые `INSERT/UPDATE/DELETE` на `tasks`, `task_status_history`, `sites` закрыты. Чтение через PostgREST также закрыто, фронтенд всё читает через бэкенд.
- Триггер на `task_status_history` запрещает `UPDATE` и `DELETE`.
- Роль хранится в `profiles`, клиент не может её менять; профиль создаётся сидом.
- Бэкенд работает под `service_role`, который обходит RLS, поэтому фильтрация по ролям выполняется в слое `application` (запросы исполнителя всегда ограничены его `assignee_id`). RLS здесь защищает от прямого доступа к Supabase API в обход бэкенда, а не от ошибок бэкенда. Это осознанный компромисс.
- Открытая регистрация отключена в настройках Auth.

### 6. Модель данных
`profiles(id, full_name, role)`, `sites(id, name, address, description, created_by, created_at)`, `tasks(id, site_id → sites on delete restrict, title, description, status, assignee_id, created_by, due_date, created_at, updated_at)`, `task_status_history(id, task_id → tasks on delete cascade, from_status, to_status, changed_by, comment, created_at)`. Статус и роль — Postgres enum. Удаление объекта с задачами запрещено ограничением `restrict`. История удаляется только каскадом при удалении самой задачи постановщиком (это внутренняя операция БД, а не API по истории).

### 7. Фронтенд: FSD
```
frontend/src/
  app/        провайдеры, роутер, guards по роли
  pages/      login, sites, site-details, task-details, my-tasks
  widgets/    task-list, task-history, site-header
  features/   auth-login, task-form, task-assign, task-change-status, task-delete, site-form
  entities/   user, site, task (типы, api, статус-бейдж), task-history
  shared/     api-клиент (fetch + токен), ui-kit, lib, config
```
Импорты только вниз по слоям, межсрезовые импорты внутри слоя запрещены; контроль линтером (Steiger или `eslint-plugin-boundaries`). Серверное состояние — TanStack Query.

### 8. Тестирование
- Сценарии из спеков (`specs/`) покрываются Playwright: каталог `e2e/` в корне репозитория. Один тест соответствует одному сценарию; название теста содержит название сценария.
- Два вида тестов Playwright: UI-тесты (браузер: вход, видимость, кнопки действий, история) и API-тесты через `request`-фикстуру (безопасность: токены, подделка статуса и истории, прямые запросы к Supabase API, видимость данных).
- Авторизация: отдельные `storageState` для постановщика и двух исполнителей, получаемые в `globalSetup` входом тестовыми пользователями.
- Данные: перед прогоном БД приводится к известному состоянию сидом (`supabase db reset` + сид), сценарии, меняющие данные, создают собственные задачи и не зависят друг от друга.
- Юнит-тесты (Vitest) остаются только для доменного слоя (переходы, роли, комментарий) — они быстрые и не требуют БД и браузера.
*Альтернатива:* интеграционные тесты API на Vitest/supertest плюс отдельные E2E — два инструмента и дублирование окружения. Отвергнуто: один инструмент покрывает и UI, и API.

### 9. Контракт фронтенд ↔ бэкенд: OpenAPI как единый источник правды
Подход code-first: контракт описывается один раз, в Zod-схемах слоя `presentation` бэкенда, всё остальное генерируется.

```
Zod-схемы DTO (backend/presentation)
   │  fastify-type-provider-zod + @fastify/swagger
   ▼
backend/openapi.json   ← генерируется скриптом, лежит в репозитории
   │  Orval
   ▼
frontend/src/shared/api/generated/   ← типы + запросы + хуки TanStack Query (не правятся руками)
```

- **Бэкенд:** маршруты Fastify описываются Zod-схемами (тело, параметры, ответы, ошибки). Те же схемы валидируют входящие запросы в рантайме и попадают в OpenAPI. Скрипт `pnpm --filter backend openapi:generate` записывает `backend/openapi.json`.
- **Фронтенд:** Orval читает `openapi.json` и генерирует TypeScript-типы, функции запросов и хуки `useQuery`/`useMutation`. Руками API-функции не пишутся. Команда `pnpm --filter frontend api:generate`.
- **Авторизация и ошибки:** один собственный fetch-мутатор в `shared/api` (подставляет JWT, разбирает ошибки API); генерируемый код его использует.
- **DTO ≠ доменные сущности:** DTO живут в `presentation` и мапятся из доменных объектов. Домен не знает про схемы и OpenAPI.
- **Единый словарь статусов и действий:** enum статусов и действий (`TaskStatus`, `TaskAction`) попадает в OpenAPI, на фронте это сгенерированные типы. Расхождения невозможны, а `availableActions` в ответе задачи типизирован.
- **Защита от рассинхронизации:** `openapi.json` и сгенерированный клиент коммитятся; проверка «после генерации нет diff» запускается перед коммитом (и в CI, если будет). Изменение API в коммите видно в diff контракта.
- **Структура FSD:** сгенерированный клиент лежит в `shared/api/generated`. Слои `entities` и `features` оборачивают хуки в осмысленные функции (например `useTask`), не импортируя детали HTTP.

*Альтернативы:* `openapi-typescript` + `openapi-fetch` — легче и без хуков, но хуки TanStack Query пришлось бы писать руками. Генерация клиента из NestJS Swagger — требует NestJS. tRPC — не подходит: нужен стандартный REST-контракт и Swagger-документация. Ручные типы на фронте — дублируют схему и расходятся.

## Risks / Trade-offs

- [Срок 2–3 часа при двух приложениях] → минимальный набор use cases, UI на готовом ui-kit без кастомной вёрстки, порядок задач по приоритету безопасности и переходов.
- [`service_role` обходит RLS, ошибка фильтрации в бэкенде открывает чужие данные] → тесты на видимость для обеих ролей, фильтры в одном месте (репозиторий принимает контекст пользователя).
- [Гонки при смене статуса] → оптимистичная проверка `expected_from_status` в `apply_task_transition`.
- [Сгенерированный код шумит в diff и ревью] → генерируемый каталог помечен как generated (`.gitattributes`), в ревью смотрится `openapi.json`.
- [Нестабильность E2E из-за общей БД] → сид перед прогоном, независимые данные в каждом тесте, запуск с одним воркером для сценариев, меняющих общие данные.
- [Холодный старт бэкенда на бесплатном хостинге] → указать в README, прогреть перед сдачей.
- [Хранение учёток тестовых пользователей] → пароли только в сообщении со сдачей, не в репозитории.
