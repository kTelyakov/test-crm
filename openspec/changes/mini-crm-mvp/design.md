# Design

## Context

Проект новый (greenfield). Мотивация и состав изменений — в `proposal.md`, требования — в `specs/`, исходное ТЗ — `docs/TZ.md`. Ограничения: срок 2–3 часа; обязательны React + TypeScript и Supabase; права и проверка переходов статусов должны работать на уровне базы, в том числе при прямых запросах к Supabase API; фронтенд по FSD, бэкенд по DDD, читаемый код; открытая регистрация отключена, серверные ключи не попадают во фронтенд и в репозиторий. Оцениваются логика, защита данных и понимание сделанного, не дизайн.

## Goals / Non-Goals

**Goals:**
- Единственный исполнитель правил доступа и переходов — база данных; обойти её нельзя ни через интерфейс, ни через бэкенд, ни прямым запросом.
- Правила переходов описаны данными в одной таблице; база их исполняет, бэкенд и интерфейс читают те же данные.
- Бэкенд тонкий и читаемый (DDD), без дублирования правил и без повышенных прав.
- Контракт фронтенд ↔ бэкенд генерируется, API-функции вручную не пишутся.

**Non-Goals:**
- Уведомления, вложения, комментарии вне истории статусов, сроки задач, отчёты, фильтры списков.
- Управление пользователями из интерфейса (пользователей создаёт администратор или сид).
- Полноценный CI/CD.

## Decisions

### 0. Технологический стек

| Область | Выбор | Почему |
|---|---|---|
| Монорепозиторий | pnpm workspaces (`frontend`, `backend`, `e2e`) | Один `install`, общие скрипты |
| Фронтенд: сборка | Vite + React 18 + TypeScript (strict) | Стандарт, быстрый старт |
| Роутинг | React Router | Простые маршруты и guards по роли |
| Серверное состояние | TanStack Query (хуки генерирует Orval) | Кэш, инвалидация после смены статуса |
| Клиентское состояние | Zustand, только сессия (пользователь, роль) в `entities/user` | Минимум кода; остальные данные серверные |
| Формы и валидация | React Hook Form + Zod | Типобезопасные формы |
| UI и стили | Tailwind CSS + shadcn/ui | Аккуратный интерфейс без ручной вёрстки |
| Контроль FSD | Steiger | Проверка границ слоёв |
| Качество кода | ESLint + Prettier | Читаемость |
| Бэкенд | Node.js, TypeScript, Fastify, Zod, `@supabase/supabase-js` | См. решения 1, 2, 9 |
| БД | Supabase Postgres: миграции, RLS, SQL-функции | См. решения 3–5 |
| Тесты | Vitest (чистая логика бэкенда), Playwright (UI и API, включая прямые запросы к Supabase) | См. решение 8 |

**Правило состояния:** серверные данные (объекты, задачи, история) живут только в TanStack Query и не дублируются в сторе; Zustand хранит только сессию; остальное — локальный `useState`. Идентификаторы берутся из URL (`useParams`), а не пробрасываются пропсами.

*Отвергнуто:* Recoil — разработка остановлена, репозиторий заархивирован; Redux Toolkit — избыточен; Jotai — равноценная альтернатива Zustand, выбран более распространённый; Ant Design/MUI — тяжелее для минимального интерфейса.

### 1. Архитектура: база защищает, тонкий бэкенд оркестрирует
```
Браузер (React, FSD)
   │  вход: Supabase Auth (anon-ключ)       данные: JWT пользователя
   ▼                                          ▼
Supabase Auth                         Тонкий бэкенд (Fastify, DDD)
                                        │  клиент Supabase создаётся
                                        │  с токеном пользователя (RLS действует)
                                        ▼
                                  Supabase Postgres
                                  RLS · task_transitions · change_task_status · триггеры
```
Бэкенд не использует `service_role`: каждый запрос выполняется от имени пользователя, поэтому RLS применяется автоматически, и права описаны один раз — в политиках. Фронтенд ходит за данными только в бэкенд (за входом — в Supabase Auth).
*Альтернативы:* бэкенд с `service_role` и проверками в TypeScript — нарушает требования ТЗ о защите в БД и дублирует правила; только Supabase без бэкенда — проще, но без DDD-слоёв, типизированного контракта и `availableActions` на сервере.

### 2. Бэкенд: DDD-модули
```
backend/src/
  modules/
    identity/   domain: User, Role | application: ResolveCurrentUser | infrastructure: проверка токена, профиль | presentation: auth-hook
    sites/      domain: Site | application: Create/Update/Delete/List/GetSite | infrastructure: SupabaseSiteRepository | presentation: routes + Zod DTO
    tasks/      domain: Task, TaskStatus, TaskAction, TransitionRule, availableActions
                application: CreateTask, UpdateTask, DeleteTask, GetTask, ListTasks, ListMyTasks, ChangeTaskStatus
                infrastructure: SupabaseTaskRepository, SupabaseTransitionRuleRepository | presentation: routes + Zod DTO
  shared/       DomainError, маппинг ошибок БД → доменные, конфиг, обработчик ошибок
```
Зависимости: `domain` ничего не импортирует из других слоёв; `application` зависит от `domain` и портов (интерфейсов репозиториев); `infrastructure` реализует порты; `presentation` вызывает use cases.

Что делает домен бэкенда: вычисляет `availableActions(task, user, rules)` по правилам, прочитанным из БД, и представляет задачи и объекты. Что он **не** делает: не проверяет переходы и права сам — решает база. `ChangeTaskStatus` вызывает функцию БД и переводит её ошибки в доменные (`TransitionNotAllowed`, `CommentRequired`, `Forbidden`).

### 3. Правила переходов как данные
Таблица `task_transitions(from_status, to_status, actor_role, requires_assignee, requires_comment)` — единственный источник правил (заполняется миграцией). Читать её могут все авторизованные пользователи, изменять — никто через API.

Функция `change_task_status(p_task_id, p_to_status, p_comment)`:
1. определяет пользователя и роль по `auth.uid()`;
2. блокирует строку задачи (`FOR UPDATE`) — исключает гонки;
3. ищет правило по (`status` задачи, `p_to_status`, роль); нет правила — ошибка `transition_not_allowed`;
4. проверяет назначенного исполнителя, если `requires_assignee`;
5. проверяет комментарий, если `requires_comment`;
6. обновляет статус и вставляет запись истории — в одной транзакции.

Ошибки — `RAISE EXCEPTION` с машинным кодом в сообщении; бэкенд маппит их в HTTP и доменные ошибки.
*Альтернативы:* правила в TypeScript и в SQL (дублирование); генерация SQL из TS-файла (лишний скрипт, когда сама таблица и есть источник).

### 4. Безопасность БД
- RLS включён на всех таблицах.
- `sites`: постановщик — полный доступ; исполнитель — `SELECT` только объектов, где у него есть задачи.
- `tasks`: постановщик — полный доступ; исполнитель — `SELECT` только своих задач, записывать не может. Статус нельзя изменить обычным `UPDATE`: у роли `authenticated` отозвано право на столбец `status`, а `INSERT` разрешён только со статусом «Новая». Автор и дата создания проставляются значениями по умолчанию (`auth.uid()`, `now()`) и не принимаются от клиента.
- Назначаемый исполнитель — только пользователь с ролью исполнителя; смена исполнителя разрешена только в статусах «Новая» и «На доработке» (триггер).
- `task_status_history`: `SELECT` по правилам видимости задачи; `INSERT/UPDATE/DELETE` для клиентских ролей отозваны, запись делает только `SECURITY DEFINER` функция перехода; дополнительно триггер запрещает `UPDATE/DELETE`.
- `profiles`: пользователь читает профили (нужны имена), роль менять не может.
- Хелперы политик (`is_manager()`, `is_assignee(task)`) — отдельные SQL-функции для читаемости.
- Открытая регистрация отключена в настройках Auth.
- `service_role` нужен только локальному сид-скрипту для создания пользователей; в репозиторий не попадает.

### 5. Модель данных
`profiles(id → auth.users, full_name, role)`, `sites(id, name, address, created_at)`, `tasks(id, site_id → sites on delete restrict, title, description, status, assignee_id, created_by, created_at)`, `task_transitions(...)`, `task_status_history(id, task_id → tasks on delete cascade, from_status, to_status, changed_by, comment, created_at)`. Статус и роль — Postgres enum. Удаление объекта с задачами запрещено ограничением `restrict`; история удаляется каскадом только вместе с задачей (операция постановщика над задачей, не прямая работа с историей).

### 6. Фронтенд: FSD
```
frontend/src/
  app/        провайдеры, роутер, guards по роли
  pages/      login, sites, site-details, task-details, my-tasks
  widgets/    task-list, task-history, site-header
  features/   auth-login, task-form, task-assign, task-change-status, task-delete, site-form
  entities/   user, site, task (типы, обёртки над хуками, статус-бейдж), task-history
  shared/     api (сгенерированный клиент + fetch-мутатор), ui-kit, lib, config
```
Импорты только вниз по слоям, межсрезовые импорты внутри слоя запрещены; контроль Steiger. Кнопки действий рисуются из `availableActions` в ответе бэкенда — правил на клиенте нет.

### 7. Атомарность и гонки
Смена статуса и запись истории выполняются одной функцией БД в одной транзакции под блокировкой строки. Два одновременных перехода по одной задаче выстраиваются в очередь, второй проверяется уже против нового статуса.

### 8. Тестирование
- Сценарии из спеков (`specs/`) покрываются Playwright (каталог `e2e/`): один тест — один сценарий, название содержит название сценария.
- Три вида тестов: UI (браузер: вход, видимость, кнопки, история); API бэкенда (`request`-фикстура); **прямые запросы к Supabase с токеном пользователя** (`supabase-js`) — проверка «в обход интерфейса»: чужие задачи, прямой `UPDATE` статуса, запись в историю, запрещённый переход.
- Авторизация: `storageState`/токены для постановщика и двух исполнителей в `globalSetup`.
- Данные: перед прогоном БД приводится к известному состоянию (`supabase db reset` + сид); сценарии, меняющие данные, создают свои задачи.
- Vitest — для чистой логики бэкенда (`availableActions`, маппинг ошибок).
*Альтернатива:* pgTAP для SQL — дополнительный инструмент; Playwright с прямыми запросами проверяет те же правила тем способом, которым их будут проверять ревьюеры.

### 9. Контракт фронтенд ↔ бэкенд: OpenAPI как единый источник правды
```
Zod-схемы DTO (backend/presentation)
   │  fastify-type-provider-zod + @fastify/swagger
   ▼
backend/openapi.json   ← генерируется скриптом, лежит в репозитории
   │  Orval
   ▼
frontend/src/shared/api/generated/   ← типы + запросы + хуки TanStack Query (не правятся руками)
```
- Бэкенд: маршруты описываются Zod-схемами (тело, параметры, ответы, ошибки); те же схемы валидируют запросы и попадают в OpenAPI. Скрипт `openapi:generate`.
- Фронтенд: Orval генерирует типы, запросы и хуки; один fetch-мутатор в `shared/api` подставляет JWT и разбирает ошибки.
- Типы БД для бэкенда генерирует `supabase gen types`.
- DTO ≠ доменные сущности: DTO живут в `presentation` и мапятся из домена.
- `openapi.json` и клиент коммитятся; перед коммитом проверяется отсутствие diff после генерации. Каталог `generated` помечен в `.gitattributes`.
*Альтернативы:* `openapi-typescript` + `openapi-fetch` (хуки пришлось бы писать руками); tRPC (нужен стандартный REST и Swagger); ручные типы (дублируют схему).

### 10. Документы для сдачи
- `README.md` — запуск, миграции, сид, тесты, деплой.
- `docs/for-manager.md` — объяснение для руководителя-непрограммиста (полстраницы, без терминов или с пояснениями): как устроена система, как защищены данные, что не может сделать исполнитель.
- `docs/DECISIONS.md` — решения и допущения там, где ТЗ неоднозначно, и что не успели.

## Risks / Trade-offs

- [Срок 2–3 часа] → минимальный набор use cases, UI на готовом ui-kit, порядок задач по приоритету безопасности и переходов.
- [Ошибка в RLS-политике открывает данные] → тесты прямых запросов от лица каждой роли (чужие задачи, запись, история) в Playwright.
- [Тонкий бэкенд добавляет деплой и холодный старт] → указать в README, прогреть перед сдачей.
- [Права доступа к столбцам и `SECURITY DEFINER` легко настроить неверно] → фиксированный `search_path` в функциях, явные `REVOKE/GRANT`, тесты на каждое запрещённое действие.
- [Сгенерированный код шумит в diff] → помечен как generated, в ревью смотрится `openapi.json`.
- [Нестабильность E2E из-за общей БД] → сид перед прогоном, независимые данные в каждом тесте.
- [Локальный Supabase требует Docker] → для тестов используется локальный Supabase; для деплоя — облачный проект.

## Open Questions

Ни один пункт не меняет спеки или состав задач:
- Хостинг: по умолчанию фронтенд на Vercel, бэкенд на Render (бесплатный план, холодный старт). Можно пересмотреть при деплое.
- Допущения, не заданные ТЗ (записываются в `docs/DECISIONS.md`): исполнитель при создании задачи обязателен; адрес объекта обязателен; смена исполнителя только в «Новая» и «На доработке»; удаление объекта с задачами запрещено; фильтры и сроки не делаем.
