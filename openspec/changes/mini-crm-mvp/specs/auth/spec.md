# Spec Delta

## Purpose

Определяет вход пользователей в систему, их роли и защиту доступа: только аутентифицированные пользователи с известной ролью получают доступ к данным, а секретные ключи остаются на сервере.

## ADDED Requirements

### Requirement: Вход по email и паролю
Система SHALL аутентифицировать пользователя по email и паролю и давать доступ к приложению только после успешного входа.

#### Scenario: Успешный вход
- **WHEN** пользователь вводит верные email и пароль
- **THEN** система открывает приложение и показывает разделы, соответствующие его роли

#### Scenario: Неверные учётные данные
- **WHEN** пользователь вводит неверный email или пароль
- **THEN** система показывает сообщение об ошибке и не создаёт сессию

#### Scenario: Неавторизованный доступ к экранам
- **WHEN** неавторизованный пользователь открывает любой экран, кроме входа
- **THEN** система перенаправляет его на экран входа

### Requirement: Открытая регистрация отключена
Система MUST NOT позволять самостоятельную регистрацию: пользователи создаются только администратором вне приложения.

#### Scenario: Попытка самостоятельной регистрации через API
- **WHEN** клиент обращается к публичному эндпоинту регистрации Supabase Auth
- **THEN** регистрация отклоняется

### Requirement: Роли пользователей
Система SHALL присваивать каждому пользователю ровно одну роль: постановщик или исполнитель. Роль MUST NOT изменяться через клиентский API. В системе может быть несколько пользователей каждой роли.

#### Scenario: Попытка изменить собственную роль
- **WHEN** авторизованный пользователь пытается изменить свою роль любым способом, включая прямой запрос к Supabase
- **THEN** запрос отклоняется, роль остаётся прежней

### Requirement: Защита API бэкенда
Каждый запрос к API бэкенда MUST содержать действительный токен пользователя. Бэкенд SHALL определять личность и роль по токену и обращаться к базе от имени этого пользователя, а не с повышенными правами.

#### Scenario: Запрос без токена
- **WHEN** клиент вызывает API без токена или с недействительным токеном
- **THEN** бэкенд отвечает ошибкой аутентификации и не возвращает данных

#### Scenario: Подмена идентичности в теле запроса
- **WHEN** клиент указывает в теле запроса чужой идентификатор пользователя
- **THEN** бэкенд игнорирует его и действует от имени пользователя из токена

### Requirement: Секреты не попадают во фронтенд и репозиторий
Ключ `service_role` и другие серверные секреты MUST NOT попадать во фронтенд-сборку и в репозиторий. Приложение (фронтенд и бэкенд) MUST NOT использовать `service_role` при обработке пользовательских запросов.

#### Scenario: Проверка репозитория и сборки
- **WHEN** в репозитории и во фронтенд-сборке ищут значение `service_role`
- **THEN** оно не найдено, а в репозитории присутствуют только файлы-примеры переменных окружения без значений
