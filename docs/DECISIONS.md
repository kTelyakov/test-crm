# Решения и допущения

Формулировки и пробелы ТЗ (`docs/TZ.md`), на которых пришлось принять решение, и то, что не сделано. Подробное обоснование архитектуры — `openspec/changes/archive/2026-11-08-mini-crm-mvp/design.md`.

## Ключевые архитектурные решения

1. **Правила живут в базе.** ТЗ требует защиты на уровне БД даже при прямых запросах к Supabase. Поэтому права (RLS), допустимые переходы (таблица `task_transitions` + функция `change_task_status`) и неизменяемость истории реализованы миграциями. Бэкенд их не дублирует.
2. **Тонкий бэкенд по DDD под токеном пользователя.** Он не использует `service_role`, поэтому RLS действует и на запросы через него. Даёт типизированный контракт (OpenAPI), единый формат ошибок и `availableActions` для интерфейса. Альтернативы: бэкенд с `service_role` и проверками в коде (дублирует правила и нарушает требования ТЗ); только Supabase без бэкенда (нет DDD-слоёв и серверного расчёта действий).
3. **Правила переходов — данные.** Изменение строки в `task_transitions` одновременно меняет проверку в базе и кнопки в интерфейсе. Это проверено тестом.
4. **Контракт генерируется:** Zod → OpenAPI → Orval. Сгенерированный клиент коммитится, повторная генерация не даёт diff.
5. **Фронтенд — FSD, состояние:** серверные данные в TanStack Query, в Zustand только сессия. Recoil отвергнут (разработка остановлена), Redux/Jotai/MUI/AntD — избыточны или равноценны выбранному.

## Допущения там, где ТЗ неоднозначно

- Таблица переходов восстановлена из описания ролей: «Новая» → «В работе», «В работе» → «На проверке», «На проверке» → «Принята» или «На доработке» (комментарий обязателен), «На доработке» → «В работе». Остальные переходы запрещены.
- Адрес объекта обязателен, как и название.
- Исполнитель обязателен при создании задачи.
- Исполнителя можно менять только в статусах «Новая» и «На доработке» (в работе и на проверке — нельзя).
- Объект, в котором есть задачи, удалить нельзя (`on delete restrict`); пустой — можно. Задачу удаляет только постановщик, вместе с историей: это единственный путь, по которому история исчезает.
- Назначать можно только пользователя с ролью исполнителя (триггер).
- Фильтры в списках, сроки задач, уведомления и вложения не делались: в ТЗ их нет.
- Постановщик не видит «Мои задачи» (раздел только для исполнителя).

## Отступления от первоначального плана

- В `entities` пока только `user`, `site`, `task`; `task-history` оформлен виджетом `widgets/task-history`, а `task-assign` слит в форму задачи (`features/task-form`): FSD запрещает импорт между слайсами одного слоя, а выбор исполнителя нужен только форме.
- Правило Steiger `insignificant-slice` отключено: пользовательские сценарии оформлены отдельными слайсами `features`, даже если их использует один экран.
- Компоненты ui-kit написаны вручную в стиле shadcn/ui (Radix + class-variance-authority + Tailwind), без CLI shadcn.
- Типы строк БД в бэкенде описаны вручную в инфраструктурных репозиториях, а не генерируются `supabase gen types`: запросы простые, а типизация вложенных выборок отнимала время.
- Встроенный Chromium Playwright не поддерживает macOS этой версии, поэтому UI-тесты идут в установленном Google Chrome (`channel: 'chrome'`).
- Бэкенд запускается через `tsx` без отдельной сборки: меньше шагов при развёртывании.

## Ограничения и что не сделано

- **Развёртывание:** Supabase cloud (миграции и сид), бэкенд на Render, фронтенд на Vercel; адреса в README. Smoke-набор `pnpm test:deployed` (9 тестов) проверен против живого приложения. Основной набор `test:e2e` против облака не запускается: он создаёт и удаляет данные, поэтому идёт только на локальном Supabase.
- **Деплой без CI:** автоматических проверок и миграций в GitHub Actions нет. Миграции накатывались вручную (`supabase db push`), Render и Vercel собирают `main` сами.
- Бесплатные планы: Render «засыпает» (первый запрос после простоя идёт до минуты), проект Supabase ставится на паузу после недели без активности и восстанавливается в дашборде.
- Работа велась в одной ветке `main`, отдельного PR нет; история коммитов описана в `docs/COMMITS.md`.
- Тест атомарности подключается к БД напрямую через `DB_URL` и работает только с локальным Supabase.
- Подготовка данных в тестах использует `service_role` (создание задач в нужном статусе и пользователей); проверяемые действия выполняются от имени ролей.
- Очень много одновременных переходов не нагружалось: проверено, что два одинаковых перехода по одной задаче дают один успех и одну ошибку.
- Нет пагинации списков, поиска, аудита удаления задач.
